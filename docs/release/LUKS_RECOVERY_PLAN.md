## 2. Risks

| Risk | Effect | Likelihood |
|---|---|---|
| Header area damaged (bad sectors at the start of `sda2`, a stray `dd`/`mkfs`/`wipefs`, an installer touching the wrong partition) | **all data unreadable, even with the right passphrase.** LUKS2 keeps two copies of its binary header + JSON metadata, but both live in the same first 16 MiB; the keyslot area exists once | low, total impact |
| Passphrase forgotten / mistyped layout | locked out; nothing else opens the container | low-medium (one keyslot, no fallback) |
| SSD failure | header and data both gone - a header backup does not help | backups of the data (Nextcloud, Git) cover it, not LUKS |
| Theft of the powered-off laptop | protected (Argon2id, no TPM auto-unlock) | - |
| Header backup or recovery key stolen | an attacker with the disk + the backup + an **old** passphrase opens it, even after that passphrase was removed from the disk (proven in 4.2) | depends on storage |

## 3. Options for this hardware

| Option | Fits? | Notes |
|---|---|---|
| **Recovery key** (`systemd-cryptenroll --recovery-key`) as a 2nd keyslot | **yes - recommended** | high-entropy, generated by systemd, 8 groups of 8 modhex letters (`cbdefghijklnrtuv` - no y/z, same keys on German and US layouts); it is an ordinary passphrase keyslot, so the busybox `encrypt` hook accepts it typed at the normal prompt (drill 4.3) |
| Second human passphrase (`cryptsetup luksAddKey`) | yes | alternative if the user prefers something memorable; same storage rules |
| **Header backup** (`cryptsetup luksHeaderBackup`) on offline media | **yes - recommended** | 16 MiB file; restores a damaged header (drill 4.1); must be refreshed after every keyslot change |
| TPM2 auto-unlock (`systemd-cryptenroll --tpm2-device`) | **no** | the T440p has TPM 1.2; systemd-cryptenroll supports TPM2 only. Would also need the `sd-encrypt` hook |
| FIDO2 token | not now | needs the `sd-encrypt` (systemd) initramfs instead of busybox `encrypt` - a boot-path change, out of release scope |
| Secure Boot | separate topic | protects the unencrypted UKI against tampering (evil maid); not a recovery measure. Later, separately (sbctl + own keys) |

## 4. Drills already run (image files on the controller, cryptsetup 2.8.7)

Throw-away 64 MiB image files, random throw-away keys, deleted afterwards -
no real secret, nothing on the laptop.

4.1 **Backup -> wipe -> restore**: LUKS2 with 2 keyslots;
`luksHeaderBackup` = 16777216-byte file; `open --test-passphrase --header
<backup>` = 0 (backup verifiable without touching the disk); first 16 MiB
zeroed -> `isLuks` = 1 (container gone); `--test-passphrase` with the
detached backup header still 0; `luksHeaderRestore` = 0; normal
`--test-passphrase` = 0.

4.2 **Stale backup**: after `luksKillSlot 1` on the disk, key 2 fails
against the disk (2) but **still opens through the old backup (0)** ->
after removing/changing a keyslot the old backup must be destroyed.

4.3 **Recovery key**: `systemd-cryptenroll --unlock-key-file=<k>
--recovery-key <img>` = 0, key format `([cbdefghijklnrtuv]{8}-){7}...`
(71 characters incl. dashes), keyslot 1 + token `systemd-recovery`;
`cryptsetup open --test-passphrase` with the key as a plain passphrase = 0
-> works with the busybox prompt.

## 5. Procedure (after the clean install, user present, approved separately)

All commands run on the laptop as root in the user's terminal; secrets are
typed or read by the user, never passed through SSH, chat, argv or files of
the agent.

0. The LUKS partition, taken from the kernel command line archinstall wrote:
   ```sh
   LUKS=/dev/disk/by-partuuid/$(sed -n 's/.*cryptdevice=PARTUUID=\([^:]*\):.*/\1/p' /etc/kernel/cmdline)
   sudo cryptsetup isLuks "$LUKS" && echo "$LUKS"
   ```
1. **Recovery key** (keyslot 2):
   ```sh
   sudo systemd-cryptenroll --recovery-key "$LUKS"
   ```
   asks for the existing passphrase, prints the key **once** on the screen
   (and a QR code). The user writes it down on paper immediately; optional
   second copy in Bitwarden (user's choice - section 6). Clear the
   terminal scrollback afterwards; do not screenshot.
2. **Verify** both keyslots without unlocking anything new:
   ```sh
   sudo cryptsetup luksDump "$LUKS" | grep -E '^  [0-9]+: luks2|systemd-recovery'
   sudo cryptsetup open --test-passphrase "$LUKS"   # passphrase -> exit 0
   sudo cryptsetup open --test-passphrase "$LUKS"   # recovery key -> exit 0
   ```
3. **Header backup** - straight onto the offline medium (a USB stick
   kept for this), never onto the laptop's own disk:
   ```sh
   sudo cryptsetup luksHeaderBackup "$LUKS" \
       --header-backup-file /run/media/medvidec/<stick>/t440p-luks-header-$(date +%F).img
   sudo cryptsetup open --test-passphrase --header /run/media/medvidec/<stick>/t440p-luks-header-*.img \
       "$LUKS"                                      # exit 0
   sha256sum /run/media/medvidec/<stick>/t440p-luks-header-*.img       # note it next to the file
   ```
   Second copy on a second offline medium (stored elsewhere).
4. **Boot test** (separately approved reboot): at the LUKS prompt the
   recovery key once (proves the busybox path), next boot the passphrase.
5. **Record** in the release report: number of keyslots, backup date +
   sha256, where (description only, not the place) - no key, no passphrase.

## 6. Storage rules

| Item | Where | Never |
|---|---|---|
| Passphrase | the user's memory + paper | repository, chat, controller, laptop files |
| Recovery key | paper in a different place than the laptop; optionally Bitwarden (encrypted vault, the user's decision) | repository, the laptop, the controller, any agent output |
| Header backup | two offline USB sticks, apart from the laptop (or a Bitwarden attachment - user's decision); treat it like a key: with an old passphrase it opens the disk | repository (public!), the laptop itself (useless when the disk dies), the controller without explicit authorization |

Refresh rule: after `luksAddKey`, `luksKillSlot`, `luksChangeKey`,
`systemd-cryptenroll --wipe-slot` or `cryptsetup reencrypt` -> new header
backup, verify, **destroy the old backups**.

## 7. Recovery procedures

| Situation | Steps |
|---|---|
| Passphrase forgotten | type the recovery key at the boot prompt; then `sudo cryptsetup luksChangeKey` / `luksAddKey` a new passphrase, remove the old slot, new header backup (section 6) |
| Prompt rejects the right passphrase | keymap: the initramfs uses `de-latin1` (vconsole.conf); from the Arch ISO try `loadkeys de-latin1` / `us` + `cryptsetup open --test-passphrase` |
| Header damaged (`cryptsetup isLuks` fails, "Device is not a valid LUKS device") | Arch ISO (`LUKS` = the internal SSD's second partition, `lsblk -o NAME,SIZE,MODEL`) -> `cryptsetup open --test-passphrase --header <backup> "$LUKS"` first (non-destructive), then `cryptsetup luksHeaderRestore "$LUKS" --header-backup-file <backup>`, boot. Do **not** run `luksFormat` or any repair tool before trying the backup |
| No backup and header damaged | data is lost; reinstall per `CLEAN_INSTALL_PLAN.md`, data from Nextcloud / Git |
| SSD dead | new SSD, `CLEAN_INSTALL_PLAN.md`; the header backup is irrelevant |
